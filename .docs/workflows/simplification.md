# 代码简化

> **触发时机**：
>
> 1. **实现前** — 用户已确认方案、开始写测试/代码之前，先走决策阶梯选最少方案；
> 2. **实现后** — 每次代码变更完成后、[完成验证](./verification.md)之前，做行为等价的局部精简。
>
> **强制性**：两段都必须执行。 **关联**：[测试驱动开发](./tdd.md)、[代码审查](./code-review.md)、[CodeGraph](./codegraph.md)、[文档维护](../MAINTENANCE.md)。
>
> **借鉴**：决策阶梯改编自 [ponytail](https://github.com/DietrichGebert/ponytail) 的实现层约束；已适配本项目的变更生命周期、TDD 与沟通规范。上游插件命令（`/ponytail`、lite/full/ultra 等）**不引入**。

## 核心原则

懒的是方案，不是理解、不是测试、不是责任。

- 在不改变已确认行为、公开接口、错误处理语义或性能目标的前提下，持续降低复杂度。
- 简化只覆盖本次触及的文件和逻辑，不以“清理”为名扩大成无关重构。
- **先读懂再偷懒**：阶梯缩短的是实现，不是阅读。须先 [CodeGraph](./codegraph.md) 建上下文、读模块活文档、沿真实调用链理解问题，再选档。
- 代码审查是推荐流程，不是本工作流的前置条件；无论是否发起审查，都不得跳过简化与重新验证。

## 实现前：决策阶梯

在理解问题之后、编写失败测试与实现之前，按顺序停在**第一档足够的方案**：

| 档  | 问题                                                     | 行动                                                                                                                |
| --- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 1   | 这件事是否需要存在？                                     | 投机性/未确认需求 → 不做，并在方案或回复中用一句话说清跳过原因（YAGNI）                                             |
| 2   | 本仓库是否已有？                                         | 复用已有 helper、composables、模式、类型（含同文件函数、邻接 export）；禁止几文件之隔再造一轮；**拆新文件不算复用** |
| 3   | VueUse / `src/utils/` / composables 或已装依赖是否已有？ | 优先复用；见 `naming-convention.md` 工具复用与 `AGENTS.md`                                                          |
| 4   | 语言/运行时标准能力是否够用？                            | 用标准能力，不引入新抽象                                                                                            |
| 5   | 平台原生或已装依赖是否够用？                             | 原生控件/CSS/现有库优先；不为几行逻辑新增依赖                                                                       |
| 6   | 能否用更短的正确实现？                                   | 优先最短且行为正确的 diff；修 bug 时修根因共用路径，而不是在每个调用点打补丁                                        |
| 7   | 以上都不行                                               | 写**刚好够用**的最少代码（默认改现有文件），并继续走 TDD                                                            |

两档都能解决问题时，选更高档（更少自建代码）并继续。

### 实现前还须遵守

- **不跳过** [变更生命周期](./change-lifecycle.md) 与用户确认；阶梯不能用来“先交懒实现再质疑已确认需求”。
- **不跳过** [TDD](./tdd.md)；非平凡逻辑仍先写失败测试。平凡单行修复可按 `AGENTS.md` 简单改动路径处理，但不得用“更少代码”取消必要测试。
- **不新增**未请求的抽象：单实现接口、单产品工厂、永不变化的配置层、为“以后”预留的脚手架。
- **删除优于堆叠**：能删错误兼容层、无价值包装就删；无聊正确优于聪明难懂。
- **新建 `src/**` 源文件前的硬门**：须能指出「改哪个现有文件会错位」（职责越界 / 错误位置 / 已有 2+ 真实调用方要抽）；否则禁止新建。测试同理：优先扩现有 `*.test.ts` 宿主。计划或对话未写明「创建 + 一行错位理由」时，不得擅自写入新路径（见 [编写计划](./writing-plans.md)）。
- **文件越少越好**，但前提是改在正确位置；错误位置上的最小 diff 不是简化，是第二个 bug。不得为对称、整洁或「以后扩展」拆文件。
- 故意留下已知上限的折中（如全局锁、朴素启发式）时，用简短中文注释标明上限与升级条件，例如：`// 简化：全局锁；吞吐成瓶颈时再按账号分锁`。

## 实现后：允许的局部简化

- 用早返回缩短不必要的嵌套；
- 合并本次触及范围内的重复逻辑；
- 删除没有业务价值的中间变量、包装层或抽象；
- 改善近期新增或修改代码的命名、结构与项目规范一致性；
- 将难读的复杂条件拆为清晰、可测试的分支；
- 对照决策阶梯复查：是否仍可用 VueUse / 本仓 `src/utils` / composables / 已装依赖替换刚写下的自建逻辑。

## 禁止边界

不得借由简化：

- 改变已确认的业务功能或用户可见行为；
- 改变对外 API、类型契约或公开接口；
- 改变错误处理、降级与异常传播语义；
- 削弱信任边界校验、防数据丢失处理、安全措施或无障碍基础；
- 牺牲已确认的性能目标；
- 重构未在本次变更范围内的历史代码；
- 引入新的依赖、运行时机制或额外功能；
- 用“更少代码”跳过 TDD、完成验证或文档同步。

用户明确要求完整版实现时，按确认方案构建，不再反复争论档位。

## 执行步骤

1. **理解问题**（实现前）：CodeGraph + 模块文档 + 真实调用链；修 bug 时先摸清共用入口与全部相关调用方。
2. **走决策阶梯**（实现前）：停在第一档足够的方案；记录刻意跳过的能力与何时再加。
3. **TDD 实现**：先红后绿，只实现已确认行为。
4. **确认范围**（实现后）：以当前需求、计划和 diff 为准，列出本次触及的文件与关键逻辑。
5. **对照行为简化**：以已有测试、规格和调用方契约为边界，实施最小的行为等价改写；复查阶梯。
6. **保护覆盖**：保留现有覆盖；如果简化触及的行为没有测试，补充能锁定原有行为的最小测试。
7. **重新验证**：运行受影响测试及完成验证要求的检查，确认简化没有回归。
8. **同步说明**：若简化改变了模块结构、关键接口或可维护性约束，同步更新对应模块文档。

如果没有可安全简化的内容，记录已检查并保持代码不变；不得为了满足流程而做无收益改动。

## 与其他工作流的关系

```text
用户确认方案
  → 理解问题 + 决策阶梯（本工作流·实现前）
  → TDD 实现
  → 局部精简（本工作流·实现后，强制）
  → 测试与完成验证
  → 代码审查（推荐：含过度工程检查）
  → 文档同步与收尾
```

- [测试驱动开发](./tdd.md) 负责在实现前定义和保护行为；本工作流不替代 TDD。
- [完成验证](./verification.md) 提供验证证据；实现后简化必须在完成验证前结束。
- [代码审查](./code-review.md) 负责独立审查规范与需求符合性，并检查过度工程；未选择审查不免除本工作流。
