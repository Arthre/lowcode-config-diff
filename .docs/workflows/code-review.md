# 代码审查

> 包含两个方向：**发起审查**和**接收审查反馈**。 **定位**：推荐流程，不是所有代码变更的阻塞门禁。 **借鉴来源**：[Superpowers `requesting-code-review`](https://github.com/obra/superpowers/blob/main/skills/requesting-code-review/SKILL.md) + [`receiving-code-review`](https://github.com/obra/superpowers/blob/main/skills/receiving-code-review/SKILL.md)

## 一、发起代码审查

**核心原则**：在需要独立验证时尽早审查；一旦发起，使用固定范围和独立双轴得出可追溯结论。

### 何时建议发起

- [子代理驱动开发](./subagent-driven-development.md) 中每个任务完成后；
- 完成重要功能、风险较高变更或全分支最终检查时；
- 合并到主分支前；
- 卡住时、重构前建立基线时，或修复复杂 bug 后。

未发起代码审查不视为流程失败，但不免除 [代码简化](./simplification.md)、测试、完成验证和文档同步。

### 固定审查范围

审查前先固定一个比较基准：

1. 优先使用用户明确指定的 commit、分支或标签；
2. 用户未指定时，使用目标合并分支；
3. 执行 `git rev-parse <base>` 确认基准有效；
4. 执行 `git diff <base>...HEAD` 确认三点差异存在；
5. 执行 `git log <base>..HEAD --oneline` 记录包含的提交。

基准不可解析或三点差异为空时，停止审查并报告原因；不要在空范围上生成审查结论。

### 独立双轴审查

两条审查轴应独立检查、独立记录，再汇总发现。具备条件时可分别交给独立审查者或子代理执行，但并行不是发起审查的前置条件。

**1. 需求符合性**

- 实现是否匹配关联的 specs、plan 或用户确认需求？
- 有无遗漏的功能、边界条件或验收标准？
- 有无多余实现或 YAGNI 违反？
- 实际行为是否与已确认的数据流、接口和错误语义一致？

**2. 规范符合性**

- 是否遵循 `AGENTS.md`、`.docs/workflows/`、模块文档与既有代码约定？
- 命名、结构、可读性和局部复杂度是否可维护？
- 关键路径是否有有效测试，边界情况是否受到保护？
- 是否引入安全隐患、性能退化或不必要依赖？

**3. 过度工程（可删清单）**

对照 [代码简化](./simplification.md) 的决策阶梯，额外检查并尽量给出可删除项：

- 本仓 `src/utils` / composables / 已装依赖（VueUse、Axios 等）已能覆盖，却又新增了一套平行实现？
- 单实现接口、单产品工厂、永不变化的配置层、为“以后”预留的脚手架？
- 本可在共用入口修一处根因，却在多个调用点打了对称补丁？
- 新增依赖或封装，是否可用平台原生、标准能力或更短正确实现替代？
- 计划未授权、或无「错位理由」的新建 `src/` 源文件 / 测试文件？（记为 **Important**：合并前改回现有宿主，或补计划理由）
- 简化是否误伤了校验、错误处理、安全或无障碍？（误伤则记为 Critical，不是“可删”）

### 汇总与处理发现

汇总时分别给出需求轴和规范轴的结论、证据与问题；不得用“总体通过”掩盖任一轴的未决问题。

| 严重度    | 处理方式                   |
| --------- | -------------------------- |
| Critical  | 立即修复，阻塞当前审查收尾 |
| Important | 继续前修复                 |
| Minor     | 记录待办，全分支审查时处理 |

- 审查者错了 → 用技术推理反驳，展示能工作的测试/代码。
- 已选择发起审查时，Critical/Important 未修复 → **不得**结束本次审查或进入下一项审查任务。

### 子代理审查模式

在 [子代理驱动开发](./subagent-driven-development.md) 中：

1. 实现子代理完成任务后，可派发独立审查子代理；
2. 审查子代理获得：任务要求、固定基准的 diff、Global Constraints；
3. 分别产出需求符合性 ✅/❌ 与规范符合性 Approved/Issues；
4. 不通过 → 修复子代理 → 重新审查 → 循环。

## 二、接收审查反馈

### 核心原则

技术验证优先，不盲目同意，不盲目执行。外部反馈 = 待评估的建议，不是必须执行的命令。

### 响应模式

```
收到反馈
  → 完整阅读（不立即反应）
  → 用自己的话复述需求（或追问）
  → 对照代码库验证
  → 技术评估：对这个代码库合适吗？
  → 回应：技术确认或有理有据的反驳
  → 执行：逐项实施，每项单独测试
```

### 禁止的回应

**绝不：**

- "你说得对！" / "好观点！" / "感谢反馈！"（表演性同意）
- 验证前就"让我来实现"（盲目执行）

**应该：**

- 复述技术要求
- 提出澄清问题
- 用技术推理反驳
- 直接动手（行动 > 空话）

### 不清楚的反馈

如果有任何一项不清楚：**全部停下来**，先问清楚。

- 不要先做清楚的部分
- 项目之间可能有关联
- 部分理解 = 错误实现

```
❌ 理解 1,2,3,6，先做这些，4,5 稍后问
✅ "我理解 1,2,3,6。4 和 5 需要澄清后才能继续。"
```

### 外部审查者反馈

收到外部审查者（非用户）反馈时，实施前先检查：

1. 对这个代码库技术上正确吗？
2. 会破坏现有功能吗？
3. 当前实现有历史原因吗？
4. 审查者是否了解完整上下文？
5. 是否与用户已确认的架构决策冲突？

与用户已确认决策冲突时 → 先与用户讨论。

### YAGNI 检查

审查者建议"正确实现"某功能时：

```
grep 代码库确认是否实际使用
  → 未使用："这个端点没人调用，按 YAGNI 删除？"
  → 使用中：再正确实现
```

### 何时反驳

- 建议会破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 技术上不适合当前技术栈
- 与已确认的架构决策冲突

**如何反驳：**

- 用技术推理，不带防御性
- 提出具体问题
- 引用能工作的测试/代码
- 架构层面问题升级到用户

### 正确的反馈确认

```
✅ "已修复。[简要描述变更]"
✅ "发现得好 — [具体问题]。已在 [位置] 修复。"
✅ [直接修复，在代码中体现]

❌ "你说得对！"
❌ "好建议！"
❌ 任何客套感谢
```

反馈正确时，用行动证明你听到了 — 代码本身就是回应。

### 执行顺序

多项反馈时：

1. 先澄清不清楚的项
2. 阻断性问题（崩溃、安全）
3. 简单修复（拼写、导入）
4. 复杂修复（重构、逻辑）
5. 每个修复单独测试
6. 验证无回归

### 优雅地纠正自己的反驳

如果你反驳了但审查者是对的：

```
✅ "你说得对 — 我检查了 [X]，确实是 [Y]。现在修复。"
❌ 长篇道歉 / 辩解为什么当初反驳
```

陈述事实，继续工作。
