# 系统化调试

> **触发时机**：遇到任何 bug、测试失败、异常行为时。 **核心规则**：找到根因之前，不尝试任何修复。 **借鉴来源**：[Superpowers `systematic-debugging`](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)

## 铁律

```
没有根因调查，不做任何修复
```

## 四个阶段

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码
   - 错误信息常常直接包含答案

2. **稳定复现**
   - 能否可靠触发？
   - 精确的复现步骤是什么？
   - 不能复现 → 收集更多数据，不猜测

3. **检查最近变更**
   - git diff、最近提交
   - 新依赖、配置变更
   - 环境差异
   - 模块解析路径是否被同名文件/目录改变（例如 `foo.ts` 覆盖 `foo/index.ts` 导出）

4. **多组件系统：添加诊断**
   - 在每个组件边界记录输入/输出
   - 运行一次收集证据，定位失败组件
   - 然后调查那个具体组件

5. **追踪数据流**
   - 错误值从哪里来？
   - 谁传入了错误值？
   - 持续往上追踪直到找到源头
   - **修在源头，不修在症状**

### 阶段 2：模式分析

1. 找到相同代码库中类似的**能工作**的代码
2. 逐项对比差异
3. 不要假设"这个不可能有影响"
4. 理解依赖和前置条件

### 阶段 3：假设与测试

1. 形成单一假设："我认为 X 是根因，因为 Y"
2. 做**最小**变更来验证假设
3. 一次只改一个变量
4. 验证通过 → 阶段 4；不通过 → 新假设（不要在上面叠加修复）

### 阶段 4：实现修复

1. 创建失败的测试用例（复现 bug）
2. 实现单一修复（针对根因）
3. 验证修复（测试通过，无回归）
4. **如果修了 3 次还没解决 → 停下来，质疑架构**
   - 每次修复暴露新问题在不同位置 = 架构问题
   - 与用户讨论后再继续

## 危险信号 — 停下来回到阶段 1

- "先快速修一下，之后再查原因"
- "试着改一下 X 看看能不能好"
- "同时改多个地方，跑一下测试"
- "应该是 X 的问题，先修了"
- "我不完全理解，但这样可能行"

**以上想法 = 回到阶段 1**
