# 编写实施计划

> **触发时机**：有需求规格/设计文档后，编码之前。 **输出**：保存到 `.docs/plans/YYYY-MM-DD-<功能名>.md` **借鉴来源**：[Superpowers `writing-plans`](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md) **关联**：[变更生命周期](./change-lifecycle.md)

**宣布开始**："使用 writing-plans 工作流编写实施计划。"

## 计划文档头部（强制）

每个计划必须以以下头部开始：

```markdown
# [功能名] 实施计划

> **给 Agent 执行者：** 必须使用 [子代理驱动开发](./subagent-driven-development.md)（推荐）或 [执行计划](./executing-plans.md) 逐步实施。步骤使用 checkbox（`- [ ]`）语法跟踪。

**日期：** YYYY-MM-DD **状态：** 待执行 **关联设计：** `.docs/specs/YYYY-MM-DD-<主题>.md` **目标：** [一句话描述要构建什么] **架构：** [2-3 句话描述方案] **技术栈：** [关键技术/库]

## Global Constraints

[从 spec 复制的项目级约束 — 版本下限、依赖限制、命名规则、文案规则、平台要求等，逐条一行，精确值从 spec 原文复制。每个任务的要求隐式包含本节。]

---
```

## 计划文档结构

### 文件结构先行

在定义任务前，先规划哪些文件需要创建/修改，每个文件负责什么：

- 设计边界清晰的单元，接口明确
- 优先小而专注的文件，而非职责过多的大文件
- 一起变更的文件放在一起，按职责拆分而非按技术层拆分
- 现有代码库遵循已有模式

### 任务粒度

**任务右划分**：任务是自带测试周期、值得一次审查的最小单元。将 setup、配置、脚手架、文档步骤并入其交付物所需的任务；仅在审查者可以独立拒绝一个任务而批准相邻任务时才拆分。

**细粒度步骤**（每步 2-5 分钟）：

- "写失败测试" — 一步
- "运行确认失败" — 一步
- "写最小实现" — 一步
- "运行确认通过" — 一步
- "提交" — 一步

### 任务模板

```markdown
### 任务 N：[组件名]

**对应需求：** [引用 specs 中 delta 条目的编号或摘要]

**文件：**

- 创建：`src/path/to/file.ts`
- 修改：`src/path/to/existing.ts:123-145`
- 测试：`src/**/xxx.test.ts`（Vitest）；并写明相关验收步骤

**接口：**

- 消费：[本任务使用的前序产出 — 精确签名]
- 产出：[后续任务依赖的 — 精确函数名、参数和返回类型]

- [ ] **步骤 1：编写失败测试** [具体测试代码]

- [ ] **步骤 2：确认失败** 运行：`pnpm test:run <路径>`；预期：FAIL / 错误信息正确

- [ ] **步骤 3：编写最小实现** [具体实现代码]

- [ ] **步骤 4：确认通过** 运行：`pnpm test:run <路径>`；预期：PASS

- [ ] **步骤 5：提交**（仅当用户明确要求时）
```

## 编写原则

### 历史需求/功能回看（强制）

在输出任何改动方案之前，必须先完成以下动作：

1. 回看该模块以往需求、历史修复、已有功能约束（文档与提交记录都要覆盖）。
2. 先输出"潜在影响清单"（会影响哪些链路、可能带来哪些行为变化）。
3. 等用户确认影响边界后，再给最终改动方案。

未完成以上步骤，不得进入实施计划编写。

### 禁止占位符

以下写法是**计划失败**，绝不允许：

- "TBD"、"TODO"、"稍后实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "为上述编写测试"（没有实际测试代码）
- "类似任务 N"（必须重复代码 — 执行者可能乱序阅读）
- 描述做什么但不展示怎么做（代码步骤必须有代码块）
- 引用未在任何任务中定义的类型、函数或方法

### 必须包含

- 精确的文件路径
- 完整的代码（不是"添加验证"这种模糊描述）
- 精确的运行命令和预期输出
- DRY、YAGNI、TDD、频繁提交

## 范围检查

如果规格涉及多个独立子系统，应拆分为独立的计划，每个计划产出可独立工作和测试的软件。每个计划对应独立的 specs/plans 文件对。

## 计划自检

写完完整计划后，用新眼光对照 spec 检查：

1. **Spec 覆盖**：spec 每个章节/需求能否指向一个任务？列出缺口。
2. **占位符扫描**：搜索计划中的禁止模式，立即修复。
3. **类型一致性**：后续任务中的类型、签名、属性名是否与前面任务定义的一致？

发现问题就地修复。发现 spec 需求无对应任务，补充任务。

## 执行交接

计划保存后，提供执行选择：

> "计划已保存到 `.docs/plans/<文件名>.md`。两种执行方式：
>
> **1. 子代理驱动（推荐）** — 每任务派发新子代理，任务间两阶段审查，快速迭代 **2. 内联执行** — 当前会话按批次执行，人工检查点
>
> 选择哪种？"

- 子代理驱动 → [subagent-driven-development](./subagent-driven-development.md)
- 内联执行 → [executing-plans](./executing-plans.md)

## 流体迭代

实施过程中发现方案需调整时，同步回写关联的 `specs/` 文档与当前 `plans/` 文件，保持产物与实现一致。
