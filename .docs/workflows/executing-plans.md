# 执行实施计划

> **触发时机**：有已编写的实施计划需要执行时（内联模式）。 **推荐替代**：[子代理驱动开发](./subagent-driven-development.md) — 平台支持子代理时优先使用。 **借鉴来源**：[Superpowers `executing-plans`](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md) **关联**：[变更生命周期](./change-lifecycle.md)

**宣布开始**："使用 executing-plans 工作流实施此计划。"

> 如果平台支持子代理（Cursor Agent、Claude Code、Codex 等），工作质量会显著更高。此时应优先使用 [子代理驱动开发](./subagent-driven-development.md)。

## 前置条件

- [Git 工作树隔离](./git-worktrees.md) 已就绪
- `.docs/plans/` 计划文档已确认
- 关联 `.docs/specs/` 设计文档可读

## 流程

### 第一步：加载并审查计划

1. 读取 `plans/` 文件及关联的 `specs/` 设计文档
2. 将计划状态改为「执行中」
3. 批判性审查 — 有疑问或顾虑先提出
4. 无顾虑则创建任务列表，开始执行

### 第二步：逐任务执行

对每个任务：

1. 标记为进行中
2. 严格按步骤执行（计划中的每一步）
3. 运行验证命令
4. 标记为完成
5. 重要任务完成后做自我审查（参考 [代码审查](./code-review.md)）

### 用户纠正后的返工

当用户指出方案或实现方式不正确时：

1. 先承认并重新定位正确职责边界，不在错误实现上继续叠加兼容层。
2. 修改代码时同步清理上一轮错误方案遗留的变量、分支、模板绑定、状态字段和文档描述。
3. 返工完成后用搜索确认旧实现关键词不再残留在相关路径中。
4. 验证通过后再总结，并明确说明已清理哪些旧逻辑。

### 第三步：完成后收尾

所有任务完成后：

- 按 [完成验证](./verification.md) 跑通证据（`pnpm lint` / `pnpm test:run` / 必要时 `pnpm build`）
- **同步（sync）**：将 specs 中的 delta 合并到 `.docs/{模块}/` 活文档
- **归档（archive）**：计划移至 `.docs/plans/archive/`，追加归档日期、关联提交/PR、验证摘要；specs 状态改为「已完成」
- 执行 [分支收尾](./finishing-branch.md)

详见 [变更生命周期 — 同步与归档](./change-lifecycle.md#同步sync规则)。

## 遇到阻塞时

**立即停止执行，报告问题：**

- 缺少依赖
- 测试失败
- 指令不清楚
- 验证反复失败

**宁可问清楚，不要猜测。**

## 何时回到审查步骤

- 用户根据反馈更新了计划
- 基本方法需要重新思考

**不要强行突破阻塞** — 停下来询问。

## 并行任务调度

如果计划中有多个独立任务（无共享状态、无顺序依赖），可参考 [并行任务](./parallel-tasks.md) 并行执行。

## 红线

- **未经用户明确同意，不要在 main/master 上直接开始实现**
- 不要跳过计划中的验证步骤
- 计划说要用某个工作流时，必须引用该工作流

## 与子代理驱动开发的对比

| 维度   | 本工作流（内联）     | 子代理驱动           |
| ------ | -------------------- | -------------------- |
| 执行者 | 当前会话             | 每任务新子代理       |
| 审查   | 人工检查点           | 每任务自动两阶段审查 |
| 适用   | 简单计划、需频繁确认 | 复杂计划、快速迭代   |
