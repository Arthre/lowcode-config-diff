# 并行任务调度

> **触发时机**：有 2+ 个独立任务，无共享状态，无顺序依赖。 **借鉴来源**：[Superpowers `dispatching-parallel-agents`](https://github.com/obra/superpowers/blob/main/skills/dispatching-parallel-agents/SKILL.md)

## 核心原则

每个独立问题域派发一个专用子代理，让它们并发工作。精确构造指令和上下文，确保子代理聚焦任务，不继承你的会话历史。

## 决策流程

```
多个任务/失败？
  └─ 它们独立吗？
      ├─ 否（相关的）→ 一起调查
      └─ 是 → 可以并行吗？
          ├─ 否（共享状态）→ 顺序执行
          └─ 是 → 并行调度
```

## 使用条件

**适合并行：**

- 3+ 个测试文件因不同原因失败
- 多个子系统独立出问题
- 每个问题可以独立理解
- 任务之间无共享状态

**不适合并行：**

- 失败相互关联（修一个可能修好其他的）
- 需要理解全局系统状态
- 任务之间会互相干扰（编辑同一文件、使用同一资源）
- 探索性调试（还不知道哪里坏了）

## 并行模式

### 1. 识别独立领域

按"什么坏了"分组，每个领域独立。

### 2. 为每个任务构造清晰指令

每个子代理需要：

- **明确范围**：一个文件或子系统
- **明确目标**：让这些测试通过 / 完成这个子任务
- **约束**：不改其他代码
- **自包含上下文**：理解问题所需的全部信息
- **输出要求**：返回根因和修复的摘要

### 3. 并行派发

**在同一轮响应中发出所有子代理派发** — 它们并发执行。

```
子代理 A："修复 src/utils/diff.ts 中路径比较的 2 处失败用例（或复现步骤）"
子代理 B："修复 src/views/HomeView.vue 相关交互回归"
子代理 C："修复 src/router/index.ts 守卫逻辑"
# 三个同时运行（任务必须真正独立）
```

一轮一个派发 = 顺序执行。一轮多个派发 = 并行执行。

### 4. 审查与集成

- 阅读每个子代理的摘要
- 验证修复之间无冲突（是否编辑了相同代码？）
- 按 [完成验证](./verification.md) 跑集成验证（`pnpm lint` / `pnpm test:run` 等）
- 集成所有变更

## 常见错误

| 错误                     | 正确做法                   |
| ------------------------ | -------------------------- |
| 范围太大："修所有问题"   | 聚焦："修 X 文件的 Y 问题" |
| 无上下文："修竞态条件"   | 提供错误信息和复现步骤     |
| 无约束：可能重构所有东西 | 约束："只改相关文件"       |
| 模糊输出："修好了"       | 明确："返回根因和变更摘要" |

## 与子代理驱动开发的区别

| 维度   | 并行任务           | 子代理驱动开发             |
| ------ | ------------------ | -------------------------- |
| 场景   | 多个独立问题/失败  | 计划中的顺序任务           |
| 并行度 | 多个子代理同时工作 | 每任务一个子代理，顺序执行 |
| 审查   | 集成后统一验证     | 每任务两阶段审查           |

**注意**：[子代理驱动开发](./subagent-driven-development.md) 中**不要**并行派发多个实现子代理 — 会冲突。

## 验证

子代理返回后：

1. 审查每个摘要 — 理解变更了什么
2. 检查冲突 — 子代理是否编辑了相同代码？
3. 运行完整套件 — 验证所有修复协同工作
4. 抽查 — 子代理可能犯系统性错误
