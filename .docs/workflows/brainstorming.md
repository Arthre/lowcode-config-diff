# 需求设计（Brainstorming）

> **触发时机**：任何创造性工作之前 — 创建功能、构建组件、添加功能、修改行为。 **硬性要求**：设计未被用户确认前，不得写任何实现代码。 **借鉴来源**：[Superpowers `brainstorming`](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md) **关联**：[变更生命周期](./change-lifecycle.md)

## 硬性门槛

```
在用户批准设计之前，不得调用任何实现工作流、写任何代码、搭建任何脚手架。
```

**反模式："太简单了不需要设计"** — 每个项目都走这个流程。todo 列表、单函数工具、配置变更也不例外。设计可以很短（几句话），但必须呈现并获得批准。

## 流程

### 1. 探索项目上下文

- 运行 `codegraph index`，用 CodeGraph 建立上下文
- 检查相关文件、文档、最近提交
- 阅读 `.docs/{模块}/` 活文档，理解当前架构与既有需求

### 2. 评估范围

- 如果需求涉及多个独立子系统，先建议拆分为子项目
- 每个子项目走独立的 设计→计划→实现 周期，各自有独立的 specs/plans 对
- 范围过大时，帮助用户分解：有哪些独立部分、如何关联、按什么顺序构建

### 3. 提问澄清（每次一个问题）

- 优先使用选择题
- 聚焦理解：目的、约束、成功标准
- **不要一次抛出多个问题**
- 一个话题需要深入探索时，拆成多个问题逐次提问

### 4. 提出 2-3 个方案

- 每个方案说明权衡取舍
- 给出推荐方案和理由
- 以对话方式呈现，推荐方案放前面

### 5. 呈现设计

- 按模块分段呈现，每段获取用户确认后再继续
- 覆盖：架构、组件、数据流、错误处理、测试策略
- **必须包含需求 Delta**（见下方）
- 按复杂度调整详略：简单的几句话，复杂的详细展开
- 设计隔离与清晰：每个单元职责单一，接口清晰，可独立理解和测试

### 6. 保存设计文档

- 保存到 `.docs/specs/YYYY-MM-DD-<主题>.md`
- 使用 [变更生命周期](./change-lifecycle.md) 中的 Specs 文档结构
- 状态标记为「草案」

### 7. Spec 自检

写入 spec 后，用新眼光快速检查：

1. **占位符扫描**：有无 TBD、TODO、不完整章节、模糊需求？立即修复。
2. **内部一致性**：各章节是否矛盾？架构是否匹配功能描述？
3. **范围检查**：是否聚焦到单个实施计划，还是需要拆分？
4. **歧义检查**：有无需求可被两种不同方式理解？若有，选定一种并写明确。

发现问题就地修复，无需重新走完整审查。

### 8. 用户审阅门槛

自检通过后，请用户审阅 spec 文件：

> "Spec 已写入 `<路径>`。请审阅，确认无修改后再编写实施计划。"

用户要求修改 → 修改后重新自检。用户批准 → 进入 [编写计划](./writing-plans.md)。

**brainstorming 的终点是 invoking writing-plans。** 不要在此之后调用其他实现工作流。

## 需求 Delta（强制）

设计文档必须包含「需求变更」章节，用 delta 表达**相对现状**改了什么。Review 时无需通读代码即可理解需求边界变化。

| 标记     | 含义                         |
| -------- | ---------------------------- |
| `+ 新增` | 此前不存在的新需求/行为      |
| `~ 修改` | 已有需求的行为或范围发生变化 |
| `- 移除` | 废弃的需求或行为             |

每条 delta 用**可验证的业务语言**描述；`~ 修改` 必须写清「从什么变成什么」。

完整模板见 [变更生命周期 — 需求 Delta](./change-lifecycle.md#需求-delta核心借鉴)。

## 流体迭代

用户反馈或实施中发现偏差时，随时回写 specs 文档，无需等前一阶段「锁死」。状态可在 `草案` / `已确认` / `实施中` 间切换。

## 设计原则

- **隔离与清晰**：每个单元职责单一，接口清晰，可独立理解和测试
- **遵循现有模式**：在现有项目中，先理解再改动，遵循已有模式
- **YAGNI**：果断删除不必要的功能设计
- **探索替代方案**：确定方案前始终提出 2-3 个选项
- **增量验证**：呈现设计，获得批准后再继续

## 在现有代码库中工作

- 修改前先探索当前结构
- 遵循现有代码模式
- 如果现有代码影响本次工作（文件过大、边界不清），在设计中包含针对性改进
- 不做无关重构
- 文件过大通常是职责过多的信号
