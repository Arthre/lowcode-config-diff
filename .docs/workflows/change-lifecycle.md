# 变更生命周期

> **触发时机**：任何涉及代码改动的需求，从探索到归档的完整周期。 **借鉴来源**：[Superpowers](https://github.com/obra/superpowers) 基础工作流 + OpenSpec OPSX 的「按变更组织产物」「需求 delta」「归档同步」理念，已适配本项目 `AGENTS.md` + `.docs/` 体系。

## 与 OpenSpec 的关系

本项目**不引入** OpenSpec CLI 或 `/opsx:*` 命令。仅借鉴其结构化变更管理思路，并与现有 CodeGraph、TDD、模块活文档体系合并。

| OpenSpec 概念   | 本项目对应                                      |
| --------------- | ----------------------------------------------- |
| `/opsx:explore` | [需求设计](./brainstorming.md) 的探索与澄清阶段 |
| `/opsx:propose` | 输出方案 + 保存 `.docs/specs/` 设计文档         |
| design + tasks  | `.docs/plans/` 实施计划                         |
| delta spec      | 设计/计划文档中的「需求变更」章节               |
| `/opsx:apply`   | [执行计划](./executing-plans.md)                |
| `/opsx:sync`    | 将 delta 合并到 `.docs/{模块}/` 活文档          |
| `/opsx:archive` | 计划移至 `.docs/plans/archive/`                 |

## 变更目录结构

每次有意义的代码改动，按变更主题组织产物（简单改动可跳过 specs，直接在聊天中确认后执行）：

```
.docs/
├── specs/                          ← 设计文档（需求 + 架构 + delta）
│   └── YYYY-MM-DD-<主题>.md
├── plans/                          ← 实施计划（任务清单 + TDD 步骤）
│   ├── YYYY-MM-DD-<主题>.md
│   └── archive/                    ← 已完成变更归档
│       └── YYYY-MM-DD-<主题>.md
└── {模块}/                         ← 模块活文档（长期真相源）
    └── README.md
```

**命名约定**：`specs/` 与 `plans/` 使用相同日期前缀和主题 slug，便于一一对应。

## 变更阶段

```
收到需求
   │
   ├─ 简单改动？（单行修复、改文案、明确单点）
   │   └─ → 聊天确认 → 直接 TDD 实现 → 更新模块文档
   │
   └─ 有意义的变更？
       │
       ├─ 1. 探索（explore）
       │      CodeGraph 建上下文 → 阅读模块文档 → 澄清需求
       │
       ├─ 2. 提案（propose）
       │      输出方案 → 保存 specs/ → 等待用户确认
       │
       ├─ 3. 隔离（worktree）
       │      [Git 工作树隔离](./git-worktrees.md) → 验证干净基线
       │
       ├─ 4. 计划（plan）
       │      用户确认后 → 编写 plans/ → 选择执行模式 → 等待用户确认执行
       │
       ├─ 5. 实施（apply）
       │      [子代理驱动开发](./subagent-driven-development.md)（推荐）或 [执行计划](./executing-plans.md)
       │      按 plans/ 逐步 TDD 实现
       │      实施中发现偏差 → 回写 specs/ 和 plans/（允许随时迭代）
       │
       ├─ 6. 验证（verify）
       │      [完成验证](./verification.md) → [代码审查](./code-review.md)
       │
       ├─ 7. 同步（sync）
       │      将 delta 合并到 .docs/{模块}/ 活文档
       │
       └─ 8. 归档（archive）
              计划移至 plans/archive/，标记完成日期与关联 PR/提交
```

**流体迭代**：任一阶段发现新信息，可回写 `specs/` 或 `plans/`，无需等前一阶段「锁死」。这与 OpenSpec OPSX「随时更新产物」一致。

## 需求 Delta（核心借鉴）

每个 `specs/` 文档必须包含「需求变更」章节，用 delta 表达**相对现状**改了什么。Review 时无需通读代码即可理解需求边界变化。

### Delta 标记

| 标记     | 含义                         |
| -------- | ---------------------------- |
| `+ 新增` | 此前不存在的新需求/行为      |
| `~ 修改` | 已有需求的行为或范围发生变化 |
| `- 移除` | 废弃的需求或行为             |

### Delta 模板

```markdown
## 需求变更

### + 新增

- [需求 1]：用户可以在 XXX 页面自定义导航顺序
- [需求 2]：导航配置持久化到后端

### ~ 修改

- [原需求] 导航列表来源：从「仅后端下发」改为「后端 + 用户自定义合并」

### - 移除

- [原需求] 固定顺序不可调整（已被自定义能力替代）

### 非目标（明确不做）

- 不支持跨租户共享导航配置
```

### 编写原则

- 每条 delta 用**可验证的业务语言**描述，避免实现细节
- `~ 修改` 必须写清「从什么变成什么」
- `- 移除` 必须说明被什么替代，或标注「彻底废弃」
- 与 `.docs/{模块}/` 现有描述冲突时，以 delta 为准（实施完成后 sync 到模块文档）

## Specs 文档结构

```markdown
# [主题] 设计

**日期：** YYYY-MM-DD **状态：** 草案 | 已确认 | 实施中 | 已完成 **关联计划：** `.docs/plans/YYYY-MM-DD-<主题>.md` **影响模块：** router, views, stores, utils, ...

## 背景与目标

[为什么要做，成功标准是什么]

## 方案概述

[2-3 句话 + 推荐方案及理由]

## 架构与数据流

[组件关系、数据流转]

## 需求变更

[+ / ~ / - delta 章节]

## 技术决策

[关键取舍、错误处理、测试策略]

## 潜在影响清单

[会影响哪些链路、可能带来的行为变化]
```

## Plans 文档补充

在 [编写计划](./writing-plans.md) 标准结构基础上，计划文档头部增加：

```markdown
**关联设计：** `.docs/specs/YYYY-MM-DD-<主题>.md` **状态：** 待执行 | 执行中 | 已完成
```

计划正文无需重复 delta，但任务应能逐项对应 specs 中的需求条目。

## 同步（Sync）规则

实施完成并验证通过后，将变更沉淀到模块活文档：

1. **新增能力** → 在 `.docs/{模块}/README.md` 补充架构说明与数据流
2. **修改行为** → 更新对应段落，删除过时描述
3. **移除能力** → 从文档中删除相关章节，必要时标注废弃原因
4. **delta 已落地** → specs 中的 `+/~/-` 条目在模块文档中变为「当前事实」描述

模块文档是长期真相源；`specs/` 记录的是**那次变更的意图**，归档后仍以模块文档为准。

## 归档（Archive）规则

满足以下全部条件后归档：

- [ ] 计划内所有任务已完成
- [ ] 完成验证已通过
- [ ] `.docs/{模块}/` 活文档已 sync
- [ ] specs 状态更新为「已完成」

归档动作：

1. 将 `plans/YYYY-MM-DD-<主题>.md` 移至 `plans/archive/`
2. 在计划文末追加：

```markdown
---

**归档日期：** YYYY-MM-DD **关联提交/PR：** [hash 或 PR 链接] **验证摘要：** [关键验证命令与结果]
```

3. `specs/` 文档保留原位（作为历史设计记录），状态改为「已完成」

## 何时可跳过

| 场景                                | 可跳过                                |
| ----------------------------------- | ------------------------------------- |
| 单行 typo、注释、格式化             | specs + plans 全部跳过                |
| 明确单点 bug 修复（影响范围已确认） | specs，保留简要 plans 或聊天记录      |
| 文档漂移修正（无代码变更）          | 直接更新模块文档                      |
| 多子系统大型变更                    | 不可跳过，且应拆为多个 specs/plans 对 |
