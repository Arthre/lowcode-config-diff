# 子代理驱动开发（Subagent-Driven Development）

> **触发时机**：有实施计划，且任务基本独立，在当前会话中执行。 **推荐**：有计划时优先使用本工作流，而非 [执行计划](./executing-plans.md) 的内联模式。 **借鉴来源**：[Superpowers `subagent-driven-development`](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)，已适配本项目。

## 核心原则

每个任务派发一个**全新的实现子代理** → 任务完成后做**两阶段审查**（规格符合性 + 代码质量）→ 全部任务完成后做**全分支审查**。

**宣布开始**："使用子代理驱动开发来执行此计划。"

## 前置条件

- [Git 工作树隔离](./git-worktrees.md) 已就绪
- `.docs/plans/` 计划文档已确认
- 关联 `.docs/specs/` 设计文档可读

## 何时使用

| 条件                             | 选择                                |
| -------------------------------- | ----------------------------------- |
| 有计划 + 任务基本独立 + 当前会话 | **本工作流**（推荐）                |
| 有计划 + 需要独立会话/人工检查点 | [执行计划](./executing-plans.md)    |
| 无计划                           | 先走 [需求设计](./brainstorming.md) |

## 流程

### 0. 计划预检

派发任务 1 之前，扫描计划中的冲突：

- 任务之间是否矛盾
- 是否违反 Global Constraints
- 计划中明确要求的内容是否会被审查标准误判

将发现的问题**一次性**呈现给用户，确认后再执行。无冲突则直接开始。

### 1. 加载计划

- 读取 `plans/` 及关联 `specs/`
- 记录 Global Constraints
- 为所有任务创建 todo 列表
- 将计划状态改为「执行中」

### 2. 逐任务循环

对每个任务：

1. **派发实现子代理** — 提供：
   - 任务在整体中的位置（一句话）
   - 该任务的完整要求（精确路径、代码、验证命令）
   - 前序任务产出的接口（函数名、类型）
   - Global Constraints
   - 报告要求（状态、提交、测试摘要）

2. **处理实现子代理状态**：

   | 状态               | 处理                                                |
   | ------------------ | --------------------------------------------------- |
   | DONE               | 进入审查                                            |
   | DONE_WITH_CONCERNS | 阅读疑虑，评估后决定是否审查                        |
   | NEEDS_CONTEXT      | 补充上下文后重新派发                                |
   | BLOCKED            | 评估：补上下文 / 换更强模型 / 拆分任务 / 升级给用户 |

3. **两阶段任务审查** — 派发审查子代理，检查：
   - **规格符合性**：是否满足 specs/plan 要求？有无多余实现？
   - **代码质量**：命名、结构、测试、YAGNI

4. **审查不通过** → 派发修复子代理 → 重新审查 → 循环直到通过

5. **标记任务完成** → 下一任务

**连续执行**：任务之间不要停下来问"是否继续"。仅在 BLOCKED、真正歧义、或全部完成时暂停。

### 3. 全分支审查

所有任务完成后，派发最终代码审查（参考 [代码审查 — 发起审查](./code-review.md#一发起代码审查)）。

### 4. 收尾

- [完成验证](./verification.md)
- sync 模块活文档 + archive 计划
- [分支收尾](./finishing-branch.md)

## 模型选择

按任务复杂度选择模型，派发时**显式指定**：

| 任务类型                     | 模型策略      |
| ---------------------------- | ------------- |
| 1-2 文件、规格完整、机械实现 | 快速/便宜模型 |
| 多文件协调、模式匹配         | 标准模型      |
| 架构判断、全分支审查         | 最强可用模型  |

**回合数比 token 单价更重要** — 审查者和从 prose 实现的开发者，至少用中档模型。

## 红线

- **绝不**跳过任务审查
- **绝不**在 Critical/Important 问题未修复时进入下一任务
- **绝不**并行派发多个实现子代理（会冲突）
- **绝不**让子代理继承整个会话历史（只给任务所需上下文）
- **绝不**在 main/master 上未经用户同意就开始实现
- 审查发现规格问题 = 任务未完成，必须修复后重审

## 与执行计划的区别

| 维度   | 子代理驱动           | 执行计划（内联）         |
| ------ | -------------------- | ------------------------ |
| 执行者 | 每任务新子代理       | 当前会话直接执行         |
| 审查   | 每任务自动两阶段审查 | 人工检查点               |
| 速度   | 快，无需等待         | 有检查点停顿             |
| 适用   | 平台支持子代理时     | 简单计划或需频繁人工确认 |
